The problem

Manual orchestration doesn't scale

Build a feature by hand and you babysit every seam — re-prompting at each handoff, eyeballing "done," watching reviewers re-find the same defects every PR. Context leaks at every hop; controls get waved through.

Manual flow before

  • Each handoff leaks context — the next step re-derives what the last knew.
  • Controls pass on judgement; under pressure, they're skipped.
  • Reviewers re-find the same defect classes every PR.
The solution

One orchestrator walks a plan

Put a thin orchestrator on the desk: it walks a durable plan — the system of record — and dispatches fresh-context agents to do the work. State lives in the plan file, controls are mechanical, and a crash resumes by re-reading it.

Orchestrated pipeline after

  • State lives in the plan file — the system of record. A crash resumes by re-reading it.
  • Controls clear on evidence — a command ran and produced a result.
  • Every escaped finding books a new plan-time control. The line tightens itself.

The orchestrator walks a tree

The walk is a tree, not a line. Control runs left → right along the phases, dipping down into each phase's agents and back up before the next — the "back and forth," no crossed wires. Pick a size; the tree grows real nesting, forking, and phases as scope rises. All of it mirrors what /develop does — lean by default, forks and ladder-climbs only where they fire.

Why it compounds

The residual-feedback flywheel

Most pipelines run at flat quality. This one compounds: every run's leftovers book new plan-time controls, the planner strengthens, and audit/tidy load amortises toward an irreducible floor. The wheel is that loop — watch the controls accrue and preventable escapes run to zero.

  1. A run settles; the audit + tidy tail logs every residual finding.
  2. Each is marked preventable (a plan check could have required it) or irreducible (the floor — "compiles but subtly wrong").
  3. For each preventable one, book the plan check that should've caught it — a mechanical grep / token / lint check beats prose.
  4. Next run, the planner satisfies the anchor — that defect class stops escaping.
Your turn

How to build your own

Strip the project specifics and this is a handful of reusable parts. Start small — one generalist executor, a plan file, real controls — then add specialists, forks, and feedback where the pain shows.

You don't have to hand-roll it. The develop plugin's /develop:init discovers your repo's real gates and scaffolds exactly this shape — fitted to your stack, not transplanted. The parts below are what it builds, so you can understand it, own it, and grow it. Jump to install ↓

Three primitives, and that's it

Everything here is one of three things. Learn the trio; the rest is composition.

skill Playbook

A reusable procedure — what runs, in what order. Called by name (/develop, /plan-work, /tidy). It directs; it rarely lifts.

e.g. /develop, /plan-work, /audit-feature

agent Worker

A desk with its own fresh context and a narrow remit. Hand it a brief, it does one job, returns a short result. One desk filling its context never touches the next.

e.g. backend-scaffolder, feature-validator, reviewers

orchestrator Conductor

The thin loop that walks the plan and dispatches the desks. It holds only phase status — never the heavy reading — so it clears dozens of agents without filling up.

e.g. the /develop main loop walking PN nodes

The unlock — forking & nesting

How one orchestrator becomes dozens of coordinated desks without filling its own context. Nesting buys depth; forking buys breadth.

Together, that's the whole trick. The orchestrator nests one executor per phase (depth, clean context per slice); audit / plan / tidy fork independent reads that converge (breadth, verification). No agent ever holds the whole book — which is why the line scales past any single context.

Ship it

Bootstrap it with /develop:init

The meta-skill that stands up a pipeline like this on a fresh codebase — orchestrator, plan contract, starter agent registry, real gates, safe hooks — by discovering your repo, not copying someone else's. Two commands: scaffold once, then run.

  1. Add the marketplace
    /plugin marketplace add chrisjenx/cjs-orchestrator
  2. Install the plugin
    /plugin install develop@cjs-orchestrator
  3. Scaffold, then run
    /develop:init — detects your stack, confirms your real gate commands, writes the per-repo config + safe hooks.
    /develop:run <spec | ticket | idea> — walks the plan, dispatches one executor per phase, runs your real gates, hands off a reviewed, committed branch.

/develop:init never transplants a finished system — it reads this repo's commands and conventions and grows from a minimal core via the feedback flywheel. Source & backlog: github.com/chrisjenx/cjs-orchestrator.
